## Task 1: How does Object-Relational Mapping (ORM) bridge the gap between object-oriented programming and relational databases, and what role does JPA play in this process?

### First, What Problem Does ORM Solve?

Applications are written using:

```text
Objects

Classes

Inheritance

Methods
```

while databases store data as:

```text
Tables

Rows

Columns

Relationships
```

There is a mismatch between:

```text
Object-Oriented World

↓

Java Objects

-------------------

Relational World

↓

Database Tables
```

---

### What Is ORM?

ORM stands for:

```text
Object Relational Mapping
```

ORM automatically maps:

```text
Java Objects

↓

Database Tables
```

and

```text
Object Fields

↓

Table Columns
```

---

### Example

Java Object

```java
Employee employee;
```

can be mapped to:

```text
EMPLOYEE Table
```

---

### ORM Flow

```text
Java Object

↓

ORM Framework

↓

SQL Query

↓

Database
```

---

### What Is JPA?

JPA stands for:

```text
Java Persistence API
```

JPA is a specification that defines:

```text
Rules

Annotations

Interfaces
```

for ORM in Java.

---

### Important Point

```text
JPA

≠

Implementation
```

JPA only defines standards.

Hibernate provides the implementation.

---

### Relationship

```text
Application

↓

JPA

↓

Hibernate

↓

Database
```

---

### Key Idea

```text
ORM

↓

Maps Objects To Tables

↓

Reduces SQL Boilerplate

--------------------

JPA

↓

Defines ORM Standards

↓

Hibernate Implements JPA
```

---

### What Is Hibernate?

Hibernate is:

```text
A JPA Implementation
```

that provides ORM functionality for Java applications.

---

### Why Is Hibernate Powerful?

Hibernate provides:

```text
Automatic ORM Mapping

Caching

Lazy Loading

Eager Loading

JPQL Support

Transaction Management
```

---

### Database Access Without Cache

```text
Application

↓

Database Query

↓

Database

↓

Return Data
```

Every request hits the database.

---

### Database Access With Cache

```text
Application

↓

Hibernate Cache

↓

Found?

↓

Yes

↓

Return Data

------------------

No

↓

Database

↓

Store In Cache

↓

Return Data
```

---

Built into Hibernate.

Scope:

```text
Session Level Cache
```

Every Hibernate session automatically uses it.

---

### Second Level Cache

Shared across multiple sessions.

Benefits:

```text
Fewer Database Calls

Faster Response

Better Performance
```

---

### Example

Without Cache

```text
Employee Id = 1

↓

Database

↓

Database

↓

Database
```

Multiple queries.

---

With Cache

```text
Employee Id = 1

↓

Cache

↓

Cache

↓

Cache
```

Much faster.

---

### Key Idea

```text
Hibernate

↓

Powerful JPA Implementation

↓

Provides ORM Features

↓

Uses Caching

↓

Reduces Database Access

↓

Improves Performance
```

## Task 3: Conceptually, how do different entity relationships (One-to-One, One-to-Many, Many-to-Many) affect database design and query complexity?

### 1. One-To-One (1:1)

One record is associated with exactly one other record.

Example:

```text
Person

↓

Passport
```

---

### Database Design

```text
PERSON

↓

PASSPORT
```

Usually uses:

```text
Foreign Key
```

---

### Query Complexity

```text
Low
```

because only one related record exists.

---

### 2. One-To-Many (1:N)

One entity can have multiple related entities.

Example:

```text
Department

↓

Employees
```

---

### Database Design

```text
Department

↓

Employee

↓

Foreign Key
```

stored in Employee table.

---

### Query Complexity

```text
Medium
```

because retrieving a department may require loading many employees.

---

### 3. Many-To-Many (N:M)

Many records relate to many other records.

Example:

```text
Students

↓

Courses

↓

Many-To-Many
```

---

### Database Design

Requires:

```text
Join Table
```

Example:

```text
STUDENT

COURSE

STUDENT_COURSE
```

---

### Query Complexity

```text
High
```

because joins are required.

---

### Comparison

| Relationship | Database Design | Query Complexity |
|-------------|----------------|------------------|
| One-To-One | Simple FK | Low |
| One-To-Many | Parent-Child FK | Medium |
| Many-To-Many | Join Table | High |

---

### Key Idea

```text
More Complex Relationships

↓

More Tables

↓

More Joins

↓

Higher Query Complexity
```

<a id="lazy-initialization-exception"></a>

## Task 6: LazyInitializationException if accessed outside transaction. When will this exception occur? During lazy or eager?

### Short Answer

```text
Lazy Loading
```

✅ Can Cause:

```text
LazyInitializationException
```

---

```text
Eager Loading
```

✅ Usually Does NOT Cause:

```text
LazyInitializationException
```

because data is already loaded.

---

### Why Does LazyInitializationException Occur?

Lazy loading delays fetching related data until it is actually accessed. 

Example:

```java
@OneToMany(fetch = FetchType.LAZY)
private List<Order> orders;
```

---

### Flow

```text
Transaction Starts

↓

Load User

↓

Transaction Ends

↓

Session Closed

↓

Access user.getOrders()

↓

Exception
```

This happens because Hibernate needs an active session to load the lazy association. 

---

### Example

```java
User user =
    repository.findById(1L);

return user;
```

Later:

```java
user.getOrders();
```

outside the transaction.

Result:

```text
LazyInitializationException
```



---

### Why Doesn't Eager Loading Usually Cause It?

With eager loading:

```java
@OneToMany(fetch = FetchType.EAGER)
```

associated data is fetched immediately when the parent entity is loaded. 

Flow:

```text
Load User

↓

Load Orders Immediately

↓

Transaction Ends

↓

Session Closed

↓

Access Orders

↓

Works
```

because data is already available.

---

### Summary

| Fetch Type | LazyInitializationException? |
|------------|-----------------------------|
| LAZY | Yes, possible |
| EAGER | Usually No |

---

### Key Idea

```text
Lazy Loading

↓

Data Loaded Later

↓

Needs Active Session

↓

Can Cause
LazyInitializationException

----------------------

Eager Loading

↓

Data Loaded Immediately

↓

Usually Avoids
LazyInitializationException
```

## Task 7: Why is the persistence context crucial in managing transactions, and how does it ensure consistency across multiple entity operations?

### First, What Is A Persistence Context?

A Persistence Context is a collection of managed entities maintained by JPA/Hibernate.

It acts as:

```text
Application

↓

Persistence Context

↓

Database
```

The persistence context is also known as:

```text
First-Level Cache
```

---

### Why Is It Important In Transactions?

During a transaction:

```text
Read Entity

↓

Modify Entity

↓

Track Changes

↓

Commit Transaction
```

The persistence context manages all these operations.

---

### How Does It Ensure Consistency?

It guarantees that:

```text
One Database Record

↓

One Managed Entity Instance
```

exists within the transaction.

This prevents conflicting versions of the same entity.

---

### Dirty Checking

Suppose:

```java
employee.setSalary(50000);
```

Hibernate detects the change automatically.

```text
Entity Modified

↓

Persistence Context Detects Change

↓

SQL Generated During Commit
```

---

### Example

```text
Transaction Starts

↓

Load Employee

↓

Update Salary

↓

Update Department

↓

Commit

↓

Database Updated
```

All operations remain consistent.

---

### Benefits

```text
Automatic Change Tracking

Reduced Database Calls

Transaction Consistency

First-Level Caching
```

---

### Key Idea

```text
Persistence Context

↓

Manages Entities

↓

Tracks Changes

↓

Coordinates Transactions

↓

Ensures Data Consistency
```

---

<a id="lazy-vs-eager-and-nplus1"></a>

## Task 8: How does the choice between lazy and eager loading impact application performance, and why does the N+1 problem occur?

### Lazy Loading

Data is loaded only when required.

Example:

```java
@OneToMany(fetch = FetchType.LAZY)
```

---

### Flow

```text
Load Department

↓

Employees Not Loaded

↓

Access Employees

↓

Load Employees
```

---

### Advantages

```text
Lower Memory Usage

Fewer Initial Queries

Better For Large Data Sets
```

---

### Disadvantages

```text
Additional Queries

Possible LazyInitializationException
```

---

### Eager Loading

Data is loaded immediately.

Example:

```java
@OneToMany(fetch = FetchType.EAGER)
```

---

### Flow

```text
Load Department

↓

Load Employees Immediately
```

---

### Advantages

```text
Data Ready Immediately

No LazyInitializationException
```

---

### Disadvantages

```text
Higher Memory Usage

May Load Unnecessary Data
```

---

### What Is The N+1 Problem?

Suppose:

```text
1 Query

↓

Load Departments
```

returns:

```text
10 Departments
```

Then for each department:

```text
1 Query

↓

Load Employees
```

---

### Result

```text
1 Query

+

10 Queries

=

11 Queries
```

This is called:

```text
N+1 Problem
```

---

### Why Does It Happen?

```text
Load Parent Entities

↓

Access Child Entities

↓

Separate Query For Each Parent
```

---

### Example

```text
Department 1

↓

Employees Query

----------------

Department 2

↓

Employees Query

----------------

Department 3

↓

Employees Query
```

and so on.

---

### Impact

```text
More Database Calls

Slower Performance

Higher Resource Usage
```

---

### Key Idea

```text
Lazy Loading

↓

Better Performance Initially

But May Cause N+1 Queries

--------------------

Eager Loading

↓

Loads More Data Upfront

↓

May Waste Resources

--------------------

N+1 Problem

↓

Many Additional Queries

↓

Performance Issues
```

---

## Task 9: Why is schema versioning important in modern applications, and how does it support continuous integration and deployment?

### First, What Is Schema Versioning?

Schema versioning is the process of tracking database structure changes over time.

Examples:

```text
Create Table

Add Column

Modify Column

Create Index
```

---

### Why Is It Important?

Applications evolve continuously.

As application code changes:

```text
Database Must Evolve Too
```

---

### Problem Without Versioning

```text
Developer A

↓

Updates Database

----------------

Developer B

↓

Different Database Structure
```

This causes inconsistency.

---

### Benefits Of Schema Versioning

#### 1. Change Tracking

```text
Version 1

↓

Version 2

↓

Version 3
```

Every change is recorded.

---

#### 2. Team Collaboration

All developers use:

```text
Same Database Structure
```

---

#### 3. Environment Consistency

```text
Development

↓

Testing

↓

Production
```

remain synchronized.

---

#### 4. Rollback Support

If something fails:

```text
Previous Version

↓

Restore
```

---

### Support For CI/CD

CI/CD requires:

```text
Automated Deployment
```

Schema versioning enables:

```text
Code Deployment

+

Database Deployment
```

to happen together.

---

### Key Idea

```text
Schema Versioning

↓

Tracks Database Changes

↓

Maintains Consistency

↓

Supports Automation

↓

Enables CI/CD
```

## Task 10: What is the conceptual difference between versioned and repeatable migrations in Flyway, and when would you use each?

### What Are Versioned Migrations?

Versioned migrations execute:

```text
Only Once
```

and have version numbers.

Examples:

```text
V1

V2

V3
```

---

### Example

```text
V1

↓

Create Employee Table
```

---

### Characteristics

```text
Executed Once

Ordered By Version

Permanent History
```

---

### What Are Repeatable Migrations?

Repeatable migrations run again whenever their contents change.

Examples:

```text
Stored Procedures

Views

Functions
```

---

### Example

```text
R__Employee_View.sql
```

---

### Characteristics

```text
No Version Number

Executed Again
When Modified
```

---

### Comparison

| Versioned Migration | Repeatable Migration |
|--------------------|---------------------|
| Runs Once | Runs When Modified |
| Uses Version Number | No Version Number |
| Schema Changes | Views, Procedures, Functions |
| Ordered Sequentially | Re-executed As Needed |

---

### When To Use Versioned Migrations?

```text
Create Tables

Add Columns

Create Constraints

Structural Changes
```

---

### When To Use Repeatable Migrations?

```text
Views

Stored Procedures

Functions

Reference Scripts
```

---

### Key Idea

```text
Versioned

↓

One-Time Schema Changes

----------------------

Repeatable

↓

Re-Executable Objects

Such As

Views

Functions

Procedures
```

## Task 11: How do Liquibase changelogs and changesets provide flexibility in managing database changes across environments?

### First, What Is Liquibase?

Liquibase is a database migration and versioning tool.

It helps manage:

```text
Database Changes

Deployments

Environment Synchronization
```

---

### What Is A Changelog?

A changelog is the master file that contains database change definitions.

Example:

```text
Changelog

↓

Changeset 1

Changeset 2

Changeset 3
```

---

### What Is A Changeset?

A changeset is an individual database change.

Examples:

```text
Create Table

Add Column

Create Index
```

---

### Example Structure

```text
Changelog

↓

Create Employee Table

↓

Add Salary Column

↓

Create Index
```

---

### Why Are They Flexible?

#### Environment Independence

Same changelog can be applied to:

```text
Development

Testing

Production
```

---

#### Automatic Tracking

Liquibase records:

```text
Executed Changesets
```

and avoids re-running them.

---

#### Controlled Deployments

Only pending changes execute.

```text
Already Applied

↓

Skip

----------------

New Change

↓

Execute
```

---

#### Easy Collaboration

Teams can contribute:

```text
Independent Changesets
```

while maintaining consistency.

---

### Deployment Flow

```text
Developer Creates Changeset

↓

Add To Changelog

↓

Deploy

↓

Liquibase Tracks Execution

↓

Database Updated
```

---

### Key Idea

```text
Liquibase

↓

Uses Changelogs

↓

Contains Changesets

↓

Tracks Database Evolution

↓

Keeps Environments Consistent

↓

Supports Controlled Deployments
```
