## Task 1: Why are legacy systems often resistant to change, and what risks do they pose to modernization efforts?

### First, What Is A Legacy System?

A legacy system is an older application that is still actively used by the organization.

It often contains:

```text
Old Technology

Old Architecture

Business-Critical Functions

Large Volumes Of Data
```

---

### Why Are Legacy Systems Resistant To Change?

#### 1. Business Dependency

Organizations rely heavily on these systems.

```text
Application Failure

↓

Business Disruption
```

---

#### 2. Complex Business Logic

Years of business rules may be embedded in the system.

```text
Hidden Rules

↓

Difficult To Modify
```

---

#### 3. Poor Documentation

Many legacy systems have:

```text
Outdated Documentation

Missing Documentation

Undocumented Features
```

making change difficult.

---

#### 4. Tight Coupling

Components are often interconnected.

```text
Change One Module

↓

Unexpected Impact

On Other Modules
```

---

#### 5. Skill Gaps

The technologies used may no longer be common.

Examples:

```text
Old Frameworks

Outdated Languages

Legacy Platforms
```

---

### Risks During Modernization

#### System Failure

```text
Modification

↓

Unexpected Issue

↓

Production Failure
```

---

#### Data Loss

Large-scale migrations may risk:

```text
Missing Records

Corrupted Data
```

---

#### Downtime

```text
Migration Activity

↓

Service Interruption
```

---

#### Increased Cost

Unexpected issues can lead to:

```text
Higher Budget

Longer Timelines
```

---

### Example

```text
15-Year-Old Banking System

↓

Millions Of Customer Records

↓

Multiple Integrations

↓

High Modernization Risk
```

---

### Key Idea

```text
Legacy Systems

↓

Business Critical

↓

Complex And Tightly Coupled

↓

Resistant To Change

↓

Increase Modernization Risk
```

```text
Large

Complex

Tightly Coupled
```

```text
Faster Delivery

↓

Short-Term Solution
```

## Task 5: What is the difference between a bug and a code smell?

### First, What Is A Bug?

A bug is a defect that causes incorrect software behavior.

Examples:

```text
Application Crash

Wrong Output

Calculation Error

Incorrect Data
```

---

### Example

Expected:

```text
10 + 20 = 30
```

Actual:

```text
10 + 20 = 50
```

This is a bug.

---

### What Is A Code Smell?

A code smell is an indicator of poor design or maintainability problems.

The application may still work correctly.

---

### Example

```java
public void processOrder() {
    // 500 lines of code
}
```

The code works but is difficult to:

```text
Read

Maintain

Modify

Test
```

---

### Comparison

| Bug | Code Smell |
|------|-----------|
| Causes Incorrect Behaviour | Does Not Necessarily Cause Failure |
| Functional Problem | Design Problem |
| Visible To Users | Often Visible To Developers |
| Must Be Fixed | Should Be Refactored |

---

### Key Idea

```text
Bug

↓

Software Behaves Incorrectly

----------------------

Code Smell

↓

Software Works

↓

Design Quality Is Poor

↓

Candidate For Refactoring
```

<a id="feature-envy"></a>

## Task 7: What is Feature Envy, and how does it indicate poor object-oriented design?

### What Is Feature Envy?

Feature Envy is a code smell where a method is more interested in another class's data than its own class's data.

---

### Example

```java
class OrderService {

    public double calculateDiscount(Customer customer) {

        if(customer.getType().equals("PREMIUM")) {
            return customer.getTotalPurchase() * 0.20;
        }

        return customer.getTotalPurchase() * 0.10;
    }
}
```

Notice that:

```text
OrderService

↓

Uses Customer Data

Again And Again
```

instead of using its own data.

---

### Why Is This A Problem?

The behavior belongs closer to:

```java
Customer
```

rather than:

```java
OrderService
```

---

### Impact On Design

#### Poor Encapsulation

```text
One Class Knows Too Much
About Another Class
```

---

#### High Coupling

```text
OrderService

↓

Strong Dependency

↓

Customer
```

---

#### Difficult Maintenance

Changes in Customer may force changes in OrderService.

---

### Refactoring Technique

```text
Move Method
```

Move the behavior closer to the data it uses.

---

### Refactored Example

```java
class Customer {

    public double calculateDiscount() {

        if(this.type.equals("PREMIUM")) {
            return this.totalPurchase * 0.20;
        }

        return this.totalPurchase * 0.10;
    }
}
```

---

### Key Idea

```text
Feature Envy

↓

Method Uses Another Class's Data
More Than Its Own

↓

High Coupling

↓

Poor OO Design

↓

Use Move Method Refactoring
```

---

## Task 8: How do Shotgun Surgery and Divergent Change differ in their impact on maintainability?

### What Is Shotgun Surgery?

One change requires modifications in many different classes.

Example:

```text
Business Rule Change

↓

Class A Updated

↓

Class B Updated

↓

Class C Updated

↓

Class D Updated
```

---

### Problems

```text
High Risk

Easy To Miss Changes

Difficult Maintenance
```

---

### What Is Divergent Change?

One class changes repeatedly for different reasons.

Example:

```java
EmployeeService
```

contains:

```text
Payroll Logic

Reporting Logic

Authentication Logic

Notification Logic
```

---

### Problems

```text
One Class

↓

Too Many Responsibilities

↓

Frequent Modifications
```

---

### Comparison

| Shotgun Surgery | Divergent Change |
|---------------|----------------|
| One Change Affects Many Classes | Many Changes Affect One Class |
| High Coupling | Low Cohesion |
| Scattered Modifications | Overloaded Class |
| Hard To Track Changes | Hard To Maintain |

---

### Key Idea

```text
Shotgun Surgery

↓

One Change

↓

Many Classes Modified

---------------------

Divergent Change

↓

One Class

↓

Many Reasons To Change
```

```text
Meaningful Names
```

## Task 12: What is a seam in legacy code, and why is it important for testing?

### First, What Is A Seam?

A seam is a location in the code where behavior can be changed without modifying the existing logic.

In simple terms:

```text
Point Of Flexibility
```

inside the application.

---

### Why Are Seams Important?

Legacy applications often have:

```text
Tightly Coupled Code

No Tests

Hardcoded Dependencies
```

making testing difficult.

---

### Example Without A Seam

```java
class OrderService {

    private PaymentGateway gateway =
            new PaymentGateway();
}
```

The dependency is hardcoded.

Testing becomes difficult.

---

### Example With A Seam

```java
class OrderService {

    private PaymentGateway gateway;

    public OrderService(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}
```

Now a test can provide:

```java
MockPaymentGateway
```

instead of the real implementation.

---

### Why Is This Useful?

#### Easier Testing

```text
Replace Real Dependency

↓

Use Mock Object

↓

Controlled Testing
```

---

#### Safer Refactoring

```text
Add Tests

↓

Refactor Code

↓

Verify Behaviour
```

---

#### Reduced Risk

Developers can modernize legacy code with greater confidence.

---

### Seam Flow

```text
Legacy Code

↓

Identify Seam

↓

Insert Test Double

↓

Create Tests

↓

Refactor Safely
```

---

### Key Idea

```text
Seam

↓

Point Where Behaviour
Can Be Replaced

↓

Supports Mocking

↓

Enables Testing

↓

Makes Legacy Code
Safer To Refactor
```

## Task 14: Write a characterization test for this method. How would you introduce a seam if the logic was buried deep in a large class?

### Given Code

```java
// Legacy code without tests

public double calculateDiscount(Customer c) {

   if(c.isPremium())
       return 0.2;
   else
       return 0.1;
}
```

---

### First, What Is A Characterization Test?

A characterization test captures:

```text
Current Behaviour

↓

Before Refactoring
```

The goal is not to change the logic.

The goal is to document how the code currently behaves.

---

### Characterization Test

```java
import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.Test;

class DiscountServiceTest {

    @Test
    void premiumCustomerShouldReceive20PercentDiscount() {

        Customer customer = new Customer(true);

        double discount =
                calculateDiscount(customer);

        assertEquals(0.2, discount);
    }

    @Test
    void regularCustomerShouldReceive10PercentDiscount() {

        Customer customer = new Customer(false);

        double discount =
                calculateDiscount(customer);

        assertEquals(0.1, discount);
    }
}
```

---

### Why Write This Test First?

Before changing legacy code:

```text
Capture Existing Behaviour

↓

Create Safety Net

↓

Refactor Safely
```

---

### What If The Logic Is Buried Deep Inside A Large Class?

Example:

```java
class OrderProcessor {

    // thousands of lines

    public void processOrder() {

        // many operations

        // discount logic hidden here

        // many more operations
```
