<a id="brownfield-vs-greenfield"></a>

## Task 1: What distinguishes a Brownfield application from a Greenfield one in terms of constraints and opportunities?

### First, What Is A Greenfield Application?

A Greenfield project is a completely new application built from scratch.

There is:

```text
No Existing Code

No Legacy Technology

No Existing Database Constraints

No Existing Business Logic
```

---

### Opportunities In Greenfield

Developers have the freedom to choose:

```text
Technology Stack

Architecture

Database

Design Patterns

Development Approach
```

---

### Greenfield Example

```text
New E-Commerce Application

↓

Built From Scratch

↓

Choose Modern Technologies

↓

Deploy
```

---

### What Is A Brownfield Application?

A Brownfield application is an existing application that is already being used in production.

Typically it contains:

```text
Existing Code

Existing Database

Existing Users

Existing Integrations

Legacy Technology
```

---

### Constraints In Brownfield

Developers cannot freely change everything because:

```text
Customers Are Using It

Business Depends On It

Existing Integrations Must Continue Working

Data Must Be Preserved
```

---

### Brownfield Example

```text
10-Year Old Banking Application

↓

Thousands Of Customers

↓

Legacy Database

↓

Modernize Existing System
```

---

### Comparison

| Greenfield | Brownfield |
|------------|------------|
| Built From Scratch | Existing Application |
| Few Constraints | Many Constraints |
| Technology Freedom | Legacy Dependencies |
| Faster Design Decisions | Careful Migration Required |
| Lower Migration Risk | Higher Migration Risk |

---

### Key Idea

```text
Greenfield
-----------
Build Something New.

Brownfield
-----------
Improve An Existing System
Without Breaking It.
```

## Task 2: Why might modernization of a Brownfield system be more complex than building a Greenfield solution?

### Greenfield Development

In a Greenfield project:

```text
Create Requirements

↓

Design Architecture

↓

Build Application
```

Everything is new.

---

### Brownfield Modernization

In a Brownfield project:

```text
Understand Existing System

↓

Understand Existing Dependencies

↓

Migrate Carefully

↓

Ensure Existing Features Still Work
```

---

### Why Is It More Complex?

#### Existing Business Logic

Many years of business rules may already exist.

```text
Must Be Preserved
```

---

#### Existing Integrations

The application may be connected to:

```text
Databases

External APIs

Third-Party Systems

Batch Jobs
```

Breaking these can impact production.

---

#### Existing Data

```text
Millions Of Records
```

cannot simply be discarded.

Data migration must be handled carefully.

---

#### Existing Users

```text
Customers

Employees

Partners
```

are already using the application.

Downtime must be minimized.

---

### Key Idea

```text
Greenfield

↓

Create New System

Brownfield

↓

Change Existing System
Without Breaking Business
```

```text

Database Drivers

External Libraries

Authentication Services

Message Queues

Third-Party APIs
```

---

### Why Do We Need To Evaluate Runtime Dependencies?

Before migrating an application, we must understand:

```text
What Does This Application Need
To Run Successfully?
```

Because moving an application without understanding its dependencies can cause failures after deployment.

---

### Example

Suppose an application depends on:

```text
Java 8

↓

Tomcat 8

↓

Oracle Database

↓

Legacy Library
```

Question:

```text
Will These Components
Work In The New Environment?
```

This must be verified before migration.

---

Application uses:


```text
Java 17
```

Potential issues:

```text
Compatibility Problems

Application Failures

Unexpected Errors
```

---

#### Example 2

Application depends on:

```text
Local File Storage
```

but cloud deployment uses:

```text
Object Storage
```

Application changes may be required.

```text
↓

↓

Compatibility Check
```

#### 2. Plan Required Upgrades

Some dependencies may be:


#### 3. Reduce Migration Risk

Understanding dependencies helps avoid:

```text
Deployment Failures

Production Incidents
```

---

#### 4. Improve Migration Planning

Teams can determine:

```text
What Must Be Migrated

What Must Be Upgraded

What Must Be Replaced
```

---

### Runtime Dependency Analysis Flow

```text

↓

```

---

### Example Architecture


## Task 19: Why might LFU eviction be more suitable than LRU eviction in recommendation systems?

### First, What Is Cache Eviction?

When cache memory becomes full:

```text
Some Data Must Be Removed
```

The policy used to remove data is called:

```text
Eviction Policy
```

---

### What Is LRU?

LRU stands for:

```text
Least Recently Used
```

It removes:

```text
Data That Has Not Been
Accessed Recently
```

---

### Example

```text
A -> Accessed 1 Hour Ago

B -> Accessed 5 Minutes Ago

C -> Accessed 10 Seconds Ago
```

LRU removes:

```text
A
```

because it was used least recently.

---

### What Is LFU?

LFU stands for:

```text
Least Frequently Used
```

It removes:

```text
Data Accessed
The Fewest Number Of Times
```

---

### Example

```text
Movie A Viewed 1000 Times

Movie B Viewed 500 Times

Movie C Viewed 2 Times
```

LFU removes:

```text
Movie C
```

because it is used least frequently.

---

### Why Recommendation Systems Prefer LFU

Recommendation systems often have:

```text
Popular Movies

Popular Products

Popular Songs
```

that are repeatedly requested.

---

### Example

```text
Trending Movie

↓

Millions Of Requests
```

Even if it wasn't accessed in the last few minutes:

```text
It Is Still Highly Valuable
```

because users frequently request it.

---

### Problem With LRU

LRU only looks at:

```text
Recent Access
```

A highly popular item might be removed if it hasn't been accessed recently.

---

### Benefit Of LFU

LFU looks at:

```text
Historical Popularity
```

and keeps frequently requested items longer.

---

### Recommendation Example

```text
Top Movie

↓

Requested 100,000 Times

↓

Keep In Cache
```

LFU handles this naturally.

---

### Comparison

| LRU | LFU |
|------|------|
| Removes Least Recently Used Data | Removes Least Frequently Used Data |
| Focuses On Recency | Focuses On Popularity |
| Good For Changing Access Patterns | Good For Consistently Popular Data |
| May Remove Popular Items | Keeps Frequently Used Items Longer |

---

### Key Idea

```text
Recommendation Systems

↓

Contain Frequently Accessed
Popular Items

↓

LFU Tracks Usage Frequency

↓

Keeps Popular Content
In Cache Longer

↓

Making LFU More Suitable
Than LRU
```

### Key Idea

```text

Changing Information
```

Sharding is the process of dividing data across multiple Redis nodes instead of storing everything on a single server.

Instead of:

```text
All Data

↓

One Redis Server
```

we use:

```text
Data Split

↓

Multiple Redis Servers
```

---

Suppose one Redis server contains:

```text

```

Eventually:

```text
Memory Limits Reached

↓

Performance Issues

↓

Scalability Problems
```

may occur.

---

### Solution: Sharding

Data is distributed across multiple Redis nodes.

Example:

```text

↓

Redis Node 1

-----------------

↓

Redis Node 2

-----------------

Product Data

↓

Redis Node 3
```

---

```text
Application

↓

↓

+-----------+
| Node 1    |
+-----------+

+-----------+
| Node 2    |
+-----------+

+-----------+
| Node 3    |
+-----------+
```

---

### How Does Sharding Improve Scalability?

#### 1. More Storage Capacity

Instead of:

```text
1 Server

↓

10 GB RAM
```

we can have:

```text
5 Servers

↓

50 GB RAM
```

combined.

---

#### 2. Better Load Distribution

Requests are spread across multiple nodes.

```text
Users

↓

Node 1

Node 2

Node 3

↓

Lower Load Per Node
```

---

#### 3. Horizontal Scaling

When more capacity is needed:

```text

↓

Distribute Data

↓

Increase Capacity
```

---

#### 4. Improved Performance

Multiple nodes can process requests simultaneously.

```text
Node 1 → Requests

Node 2 → Requests

Node 3 → Requests
```

instead of a single server handling everything.

---

Redis uses:

```text

```

Example:

```text

↓

Hash Function

↓

Node 1

-----------------

User:205

↓

Hash Function

↓

Node 2
```

```text
↓

Node 3
```

```text

Replication

Failover

Cluster Monitoring
```

```text
↓

All Data
```

Simple but limited.

With Sharding:

```text

↓

Redis Cluster

Node 1

Node 2

Node 3

Distributed Data
```
